The exact 2026 US Santa Fe Hybrid manual documents holding smart-key Unlock for more than three seconds to lower windows; release stops movement and the doors also unlock. This establishes the nearby smart-key function, not a Bluelink cloud command: https://ownersmanual.hyundai.com/full_webhelp/MX5aHEV/2026/en_US/id89527f8fde7.html . The US ccNC Door/Open Windows Remotely setting similarly refers to holding the smart key: https://ownersmanual.hyundai.com/ivi/ccNC/AVNT/USA/English/Settings_vehicle.html . Do not assign another model's remote-close behavior or the remote-start distance to windows.

No verified US window-actuation endpoint was found. Primary regional implementation: https://github.com/Hyundai-Kia-Connect/hyundai_kia_connect_api/blob/6b966c021bd3e2e7fd39c979b2abb3defeab8a2b/hyundai_kia_connect_api/HyundaiBlueLinkApiUSA.py . Hyundai Australia explicitly advertises app window control at https://www.hyundai.com/au/en/owning/bluelink ; that regional capability must not be assumed to apply to a US account or vehicle. Generic manager methods and window-status flags are not proof of actuation.

Source-backed US candidates, none newly verified on Jon's vehicle:

- Lights: POST /ac/v2/rcs/rhl/light, with LIGHTS_ONLY transaction polling. Horn plus lights: POST /ac/v2/rcs/rhl/hnl, with HORN_AND_LIGHTS polling. Existing API Lab has source-backed recipes; the emergency web controls do not currently include them.
- Locate car: GET /ac/v2/rcs/rfc/findMyCar. Preserve timestamp and rate-limit handling; location belongs behind private access, outside public status.
- Remote surround-view snapshots: GET /ac/v2/svm/getSVMDetails and POST /ac/v2/svm/findMyCarSVM, followed by timestamp-based result reads. This is a still image, not a verified video stream. Vehicle hardware, enabled remote service, explicit capture acknowledgment and duplicate protection matter. Images must stay private. General US MyHyundai guidance confirms Surround View Monitor only on supported vehicles: https://owners.hyundaiusa.com/us/en/resources/technology-and-navigation/getting-to-know-the-redesigned-myhyundai-app .
- Richer remote-start presets: the US start payload includes heating1 and four seatHeaterVentInfo values, in addition to temperature, duration and defrost. Current confirmed project recipes intentionally send heating/seat values as zero. Seat heat/ventilation and steering-wheel/rear-defrost options require vehicle-specific verification before enabling. Shared sources disagree on combined heating codes 1 versus 4 by region; do not guess. A generic steering_wheel option exists but is not serialized by the reviewed US implementation.
- Four individual window-open indicators are a reasonable read-only status addition if returned. They are not window commands.

EV charging and EV trip requests are not relevant to this non-plug-in hybrid. No implemented US navigation, valet, frunk, sunroof, remote-parking or window-closing request was established by this review. Generic or non-US feature lists cannot supply that evidence. An official app feature, such as destination sending, also does not automatically supply a tested request recipe for this project.

Next step for windows: inspect the vehicle's existing enrollment/capability fields and current US app request definitions for a concrete supported command. Capability flags remain clues until the actual request and result are established. Only then add a password-protected, single-use Render action and matching website button through the existing command guard/result flow. A physical device operating a spare smart key near the parked car is a separate possible hardware workaround, inferred from the documented fob behavior, not a researched or tested project implementation; it would also unlock the doors. The external browser now sends only a bare semantic command after the original prefix, for example `hyundai=:=unlock` or `hyundai=:=ignition_on`.
