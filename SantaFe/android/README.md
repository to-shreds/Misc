# Santa Fe API Lab for Android

Install [SantaFe-API-Lab-0.3.3.apk](https://to-shreds.github.io/Misc/SantaFe/android/dist/SantaFe-API-Lab-0.3.3.apk), open **Santa Fe API Lab**, and enter your MyHyundai email, password and four-digit Bluelink service PIN in **Account settings**. Leave **Remember account on this phone** checked and tap **Save account** or **Connect**. The account is then available without retyping; saved password/PIN are not displayed in the form. Connect performs login, enrollment and cached-status reads. Use **Run read tests** for another read pass, then **Export log** to choose a JSON file location. If login succeeds but vehicle enrollment fails, tap **Test alternate lookup** to make one read-only comparison using the same session. Connect uses the literal `@` path that succeeded in the phone log. The optional comparison changes only the `@` representation; it sends no password again and no vehicle command. A valid returned vehicle list enables that format for this session, then reads cached status when a vehicle is selected. Errors show the failed step and Hyundai’s error subcode/message. Export and share the sanitized log after the comparison. Earlier 0.3.0, 0.3.1 and 0.3.2 releases are preserved in `dist/`.

The same HTML tester is bundled inside the APK. It does not load the GitHub page, download scripts, require a browser extension, run a server, or use a cloud relay. Android 8 or later and a working system WebView are required. The app requests only Internet permission. Switching apps and opening the file picker preserve the live login. If Android destroys the activity/process or the app is closed with Back, the token is lost; saved account details let the next Connect sign in without retyping. Expired sessions likewise require Connect. No login or command is automatically retried.

Remote controls remain separate, manually confirmed tests. They operate the actual vehicle. Climate start requires outdoor acknowledgement. Cached timestamps control freshness; accepted HTTP requests do not establish physical completion. Unknown outcomes never cause an automatic retry. If the app closes during a command, check the car before acknowledging the warning and sending another command.

## Credential handling and restrictions

The bundled HTML and native transport necessarily handle account credentials. They send them only to the allowlisted Hyundai HTTPS host. With remembering enabled, email/password/PIN are encrypted with AES-256-GCM under a nonexportable Android Keystore key, using a fresh provider-generated nonce and authenticated record header. Only ciphertext is written atomically to app-private no-backup storage. Session tokens are never saved. Password/PIN fields are cleared after connection attempts. The live WebView is paused on leaving the foreground and resumed on return; destruction closes transport and clears its session. A submitted car command cannot be recalled by closing the app.

The WebView loads only the three installed assets at a synthetic HTTPS origin. Other resources, navigation, frames, workers, browser network requests, file/content access, popups and permission requests are blocked. The native bridge validates destinations, methods, headers, lengths and request bodies before opening a connection. HTTPS uses Android's normal system CA trust and hostname verification. Redirect following, HTTP caching and cookie sessions are disabled. POST bodies use fixed-length streaming; there is no application retry loop. No custom trust manager or certificate-validation bypass is present.

Saved encrypted account details, sanitized logs and a minimal unresolved-command marker are stored locally. **Disconnect** keeps the saved account but clears the live session. **Forget saved account** deletes saved ciphertext/key and clears the current session, while preserving any unresolved-command warning. Backup and device transfer are excluded. Autofill and WebView form restoration are disabled. Screenshots and recent-app previews are blocked because the page displays account and vehicle information. Log exports use Android's document picker with no broad storage permission. A destination chosen there may be a cloud provider; choose local Downloads if you want the exported log to stay on the phone.

Jon's supplied logs confirm login, enrollment and status reads. He reports both lock and unlock worked; lock polling reached SUCCESS, while the recorded unlock poll remained PENDING. The other controls remain manual acceptance tests. Automated fixtures use only synthetic accounts and never contact a real vehicle.

## Build and maintain

`./build.sh` compiles directly with JDK 17, Android platform 35 and build-tools 35.0.0. Set `ANDROID_SDK_ROOT` to an existing SDK. `tools/provision-sdk.sh` obtains build tools from the official Google repository and verifies pinned SHA-256 values. No Gradle/Maven or runtime third-party dependencies are needed. HTML/JavaScript/CSS are copied from the parent SantaFe folder into the APK during the build, so there is one canonical tester implementation.

Application ID: `com.jon.santafelab`. Version: `0.3.3`, version code `6`, min SDK `26`, target SDK `35`.

Restore the existing private signing identity before rebuilding updates. It is preserved privately as **SantaFe-API-Lab-private-update-key.zip** in Jon's files. Set `SF_SIGNING_DIR` to its extracted private directory. Never put that archive, its keystore or its password in git. The public signing-certificate SHA-256 is `90ba911d370453290457ea862344a7cbc4aca6f6f49931725b76a91b599c952d`.

Verification results are in `../docs/verification/android-verification.json` and `../docs/TEST_REPORT.md`. Account and physical vehicle tests must not be performed by synthetic instrumentation. Preserve the older Tasker project, simulator, bridge and userscript; those are separate from this Android tester.
